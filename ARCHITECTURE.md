# RMWestVoice Architecture

This document describes the current technical architecture of RMWestVoice. It reflects the stabilized pre-research codebase and intentionally avoids proposing final sound-design decisions.

For build and usage instructions, see [README.md](README.md).

For the post-research implementation sequence, see [POST_RESEARCH_ROADMAP.md](POST_RESEARCH_ROADMAP.md).

## High-Level Overview

RMWestVoice is a JUCE audio plugin project built as an instrument. The plugin accepts MIDI input, generates audio internally, and outputs audio as a synth. It does not process incoming audio and does not emit MIDI.

The core runtime flow is:

```text
MIDI input
  -> juce::Synthesiser
  -> SynthVoice
  -> OscData
  -> Gain
  -> ADSR
  -> Low-pass filter
  -> High-pass filter
  -> Master volume
  -> Audio output
```

The UI controls are connected to processor parameters through `AudioProcessorValueTreeState` attachments. The processor reads the current APVTS values during `processBlock` and applies them to the voice, oscillator, envelope, filters, and final gain.

## Main Modules

### `RMWestVoiceAudioProcessor`

Files:

```text
RM West Voice/Source/PluginProcessor.h
RM West Voice/Source/PluginProcessor.cpp
```

The processor is the plugin's central owner of audio state and parameters. Its responsibilities are:

- Declaring the plugin as a synth/instrument.
- Creating and owning the `AudioProcessorValueTreeState`.
- Creating the synth voice and synth sound.
- Preparing voices and filters for playback.
- Reading parameter values during audio processing.
- Rendering MIDI-triggered synth audio.
- Applying the filter chain and master gain.
- Saving and restoring plugin state.

Important members:

| Member | Purpose |
| --- | --- |
| `juce::Synthesiser synth` | Owns the active synth voices and sounds. |
| `AudioProcessorValueTreeState apvts` | Owns parameters and serializable plugin state. |
| `FilterData lowPassFilter` | Post-synth low-pass filter object. |
| `FilterData highPassFilter` | Post-synth high-pass filter object. |

### `RMWestVoiceAudioProcessorEditor`

Files:

```text
RM West Voice/Source/PluginEditor.h
RM West Voice/Source/PluginEditor.cpp
```

The editor owns the visual components and arranges them in the plugin window. It does not own parameter state directly. Instead, it passes the processor's APVTS into child components so they can create slider and button attachments.

Current child components:

- `OscComponent`
- `AdsrComponent`
- `FilterComponent`

The editor also draws the background image and title using binary assets generated by CMake/JUCE.

### `SynthVoice`

Files:

```text
RM West Voice/Source/SynthVoice.h
RM West Voice/Source/SynthVoice.cpp
```

`SynthVoice` inherits from `juce::SynthesiserVoice`. One voice is currently added in the processor constructor.

Responsibilities:

- Accepting only `SynthSound` instances in `canPlaySound`.
- Translating MIDI note numbers into oscillator frequency.
- Triggering ADSR note-on and note-off.
- Preparing oscillator and gain DSP objects.
- Rendering a block of oscillator audio into a temporary buffer.
- Applying gain and ADSR.
- Mixing the rendered voice into the output buffer.

Current voice processing order:

```text
OscData::getNextAudioBlock
  -> voice gain
  -> ADSR envelope
  -> mix into plugin output buffer
```

The gain inside the voice is currently fixed at `0.3f`. The user-facing `VOLUME` parameter is applied later in the processor as master gain.

### `SynthSound`

File:

```text
RM West Voice/Source/SynthSound.h
```

`SynthSound` inherits from `juce::SynthesiserSound`. It currently allows all notes and all MIDI channels.

The class is intentionally minimal. Its main architectural role is to give `SynthVoice::canPlaySound` a concrete type to validate.

## Data / DSP Layer

### `OscData`

Files:

```text
RM West Voice/Source/Data/OscData.h
RM West Voice/Source/Data/OscData.cpp
```

`OscData` inherits from `juce::dsp::Oscillator<float>`. It currently owns:

- The primary oscillator function.
- A secondary FM oscillator object.
- A simple LFO oscillator object.
- Detune state.
- Last played MIDI note.
- Internal FM and LFO modulation values.

Current oscillator mode behavior:

| Input | Behavior |
| --- | --- |
| `DAY == true` | Uses the current triangle-like waveform branch. |
| `DAY == false` | Uses the current ramp-like waveform branch. |

The processor currently calls `setWaveType(dayValue)` but does not read `NIGHT` directly. `DAY` and `NIGHT` are attached to UI radio buttons, but the processor's DSP decision is driven by `DAY`.

Current modulation notes:

- LFO is prepared through `prepareLFO`.
- LFO frequency is fixed at 5 Hz.
- LFO modulation is applied continuously during `getNextAudioBlock`.
- FM parameter objects exist in the APVTS.
- FM update is currently not enabled in the processor.

This design is intentionally documented as transitional. The FM and LFO model should be revisited after the research phase rather than expanded casually.

### `AdsrData`

Files:

```text
RM West Voice/Source/Data/AdsrData.h
RM West Voice/Source/Data/AdsrData.cpp
```

`AdsrData` wraps JUCE ADSR behavior and exposes an `updateADSR` method. The voice owns an `AdsrData` instance and updates it from APVTS values during processing.

Current parameter units:

| Parameter | Unit |
| --- | --- |
| `ATTACK` | Seconds |
| `DECAY` | Seconds |
| `SUSTAIN` | Normalized level |
| `RELEASE` | Seconds |

The UI suffix has been aligned so time parameters are shown in seconds.

### `FilterData`

Files:

```text
RM West Voice/Source/Data/FilterData.h
RM West Voice/Source/Data/FilterData.cpp
```

`FilterData` wraps a `juce::dsp::StateVariableTPTFilter<float>`.

Responsibilities:

- Preparing the filter with a JUCE `ProcessSpec`.
- Processing an audio buffer in place.
- Updating filter type, cutoff, and resonance.
- Resetting internal filter state.

The processor owns two filter instances:

- `lowPassFilter`
- `highPassFilter`

Despite these member names, both use the same `FilterData` implementation and can technically select low-pass, band-pass, or high-pass behavior through their type parameters. The defaults currently make the first filter low-pass and the second high-pass.

## UI Layer

The UI layer is located in:

```text
RM West Voice/Source/UI
```

### `OscComponent`

Owns oscillator-related controls:

- `DAY`
- `NIGHT`
- `DETUNE`

`DAY` and `NIGHT` are configured as a radio pair in the UI. `DETUNE` changes its displayed text between the current in-tune and detuned states.

### `AdsrComponent`

Owns ADSR controls:

- `ATTACK`
- `DECAY`
- `SUSTAIN`
- `RELEASE`

Each control is attached to the APVTS through `AudioProcessorValueTreeState::SliderAttachment`.

### `FilterComponent`

Currently exposes:

- `LP_FILTERFREQ`
- `VOLUME`

The APVTS also contains additional low-pass and high-pass filter type/resonance/cutoff parameters. Not all of those parameters are surfaced by the current UI.

### Look-And-Feel Classes

The project contains custom JUCE look-and-feel classes:

```text
CustomLookAndFeelDetune.h
CustomLookAndFeelOsc.h
CustomLookAndFeelViolet.h
CustomLookAndFeelYellow.h
```

These classes draw rotary sliders, labels, text editors, and buttons using the current visual style and bundled fonts.

## Parameter Ownership

All plugin parameters are created in:

```text
RMWestVoiceAudioProcessor::createParams()
```

The APVTS is the source of truth for:

- UI attachments.
- DAW-visible parameters.
- Automation.
- Preset/session state.

The current parameter set is:

| ID | Type | Default | Notes |
| --- | --- | --- | --- |
| `DAY` | Bool | `true` | Main oscillator branch used by DSP. |
| `NIGHT` | Bool | `false` | UI radio partner, not read directly by DSP. |
| `DETUNE` | Bool | `false` | Enables detune behavior in `OscData`. |
| `OSC1FMFREQ` | Float | `0.0` | Present but not currently applied by processor. |
| `OSC1FMDEPTH` | Float | `0.0` | Present but not currently applied by processor. |
| `ATTACK` | Float | `0.1` | ADSR attack time in seconds. |
| `DECAY` | Float | `1.0` | ADSR decay time in seconds. |
| `SUSTAIN` | Float | `0.8` | ADSR sustain level. |
| `RELEASE` | Float | `0.2` | ADSR release time in seconds. |
| `LP_FILTERTYPE` | Choice | `0` | Low-pass filter object type. |
| `LP_FILTERFREQ` | Float | `4800.0` | Low-pass filter object cutoff. |
| `LP_FILTERRES` | Float | `1.0` | Low-pass filter object resonance. |
| `HP_FILTERTYPE` | Choice | `2` | High-pass filter object type. |
| `HP_FILTERFREQ` | Float | `250.0` | High-pass filter object cutoff. |
| `HP_FILTERRES` | Float | `1.0` | High-pass filter object resonance. |
| `VOLUME` | Float | `0.6` | Final master gain. |

Parameter IDs should be treated as stable once public presets or DAW projects depend on them. Future renames should include a migration strategy.

## Audio Processing Flow

### Preparation

During `prepareToPlay`:

1. The synth playback sample rate is set.
2. Each `SynthVoice` is prepared.
3. Each voice oscillator's LFO is prepared.
4. The high-pass and low-pass filter objects are prepared.

### Per Block

During `processBlock`:

1. Unused output channels are cleared.
2. The processor iterates over voices.
3. Current APVTS values are read.
4. The oscillator wave branch and detune state are updated.
5. ADSR values are updated.
6. The JUCE synthesiser renders MIDI-triggered audio.
7. The low-pass filter object processes the buffer.
8. The high-pass filter object processes the buffer.
9. The `VOLUME` gain is applied.

## State Persistence

State persistence is implemented in the processor:

```text
getStateInformation
setStateInformation
```

The implementation uses APVTS state serialization:

```text
apvts.copyState()
  -> ValueTree XML
  -> binary block
```

Restore path:

```text
binary block
  -> XML
  -> tag validation
  -> apvts.replaceState(...)
```

This is the expected JUCE pattern for simple parameter-state persistence.

## Build Architecture

The current tracked build entrypoint is:

```text
RM West Voice/CMakeLists.txt
```

Important build decisions:

- C++17 is required.
- JUCE8 is added with `add_subdirectory`.
- Binary assets are compiled with `juce_add_binary_data`.
- Plugin formats are limited to `VST3` and `Standalone`.
- VST3 uses JUCE8's bundled VST3 SDK.
- `COPY_PLUGIN_AFTER_BUILD` is disabled.
- `JUCE_VST3_CAN_REPLACE_VST2=0` is explicitly defined.

The `.jucer` file remains in the repository and is aligned with the same metadata, but the current reliable build path is CMake.

## Known Technical Debt

### `DAY` / `NIGHT` Parameter Model

`DAY` and `NIGHT` are represented as two separate boolean parameters. The UI treats them as a radio pair, but the DSP currently reads only `DAY`.

Future options:

- Replace with a single `AudioParameterChoice`.
- Keep the current pair and explicitly derive a single internal mode.
- Add migration logic if public compatibility becomes important.

This should be decided during the post-research sound architecture pass.

### FM Parameters

`OSC1FMFREQ` and `OSC1FMDEPTH` exist in the parameter layout, but processor-side FM application is currently disabled.

This is documented rather than removed because deleting or renaming parameters can break future preset compatibility and because the final modulation model has not been researched yet.

### Fixed LFO Behavior

The current LFO is internal to `OscData` and fixed at 5 Hz. It is not exposed as a user parameter.

The final vibrato/LFO behavior should be designed after source-backed research into the target lead style.

### Limited Polyphony

The processor currently adds one voice. This fits a lead-prototype mindset but is not a final statement about mono, legato, glide, or polyphonic behavior.

### UI Coverage

The APVTS contains more filter parameters than the UI currently exposes. This mismatch should be resolved during a UI/parameter design pass.

### Presets

The plugin supports DAW state persistence through APVTS serialization, but it does not yet include a first-party preset browser or preset file format.

## Deferred Sound Architecture Decisions

The following decisions are intentionally out of scope for this cleanup stage:

- Portamento/glide.
- Legato behavior.
- Pitch bend range and response.
- Controllable vibrato.
- Oscillator selection and historically grounded waveform choices.
- Saturation/nonlinear color.
- Effects such as chorus, delay, or reverb.
- Preset vocabulary and default patch design.
- Detailed matching to any historically relevant synth lead sources.

Those items should be handled after the deep research phase, using source-backed references rather than casual assumptions.

## Maintenance Guidelines

When changing this codebase:

- Keep infrastructure changes separate from sound-design changes.
- Avoid changing parameter IDs without a migration plan.
- Prefer JUCE/APVTS idioms over ad hoc state handling.
- Keep generated build files out of source control.
- Update this document when ownership, signal flow, or parameter behavior changes.
- Verify both Standalone and VST3 targets after build-system changes.
